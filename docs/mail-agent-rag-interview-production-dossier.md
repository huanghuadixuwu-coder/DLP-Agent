## 当前生产契约（本节优先）

> **证据优先级：** 本节是当前设计/计划的压缩索引；下文历史数字只作为计划完成后的证据形状。任何与本节冲突的版本指向记录、顺序、名单或日历陈述均已失效。

- 客户公共邮箱名单只由一次完整、非分页的公共邮箱名单接口（实现标识：`publicmail/get`）单对象响应证明：精确 28 名直接用户，部门和标签列表为空。同应用另建服务商专用、探测专用的探针邮箱，禁止客户内容、产品、IMAP、发送及试点组；客户名单始终只有这28人且不适用分页证据。
- 日历是 42 天人工且 AI 关闭的基线期、预先固定的非零且 ≤24h 过渡期、42 天试点期、三个独立 7 天跟踪期，汇总约 13 周就绪后时间加过渡期。每个受理事件原子写入可处理性判定（实现标识：`ActionabilityDecision`）的三分类：可处理事件、不可处理事件（实现标识：`NON_ACTIONABLE`）和待确认事件；只排除闭集不可处理事件，待确认事件留在主分析且由人工处理、AI 关闭。
- 审批通过记录（实现标识：`ApprovalGrant`）与审批拒绝记录（实现标识：`ApprovalDenial`）互斥 CAS；审批拒绝记录不授权、不新建请求。非发送终态只能由显式处理结论（实现标识：`HandlingResolution`）写入，待发送状态（实现标识：`SEND_PENDING`）阻断且不得推断。
- 企业微信仅最新的有效状态（实现标识：`status=1`）可授权（读取/变更 ≤60s，复核/审批/发送 ≤30s）。活动区间（实现标识：`ActivityInterval`）使用隐私安全事件和服务端时间、跨浏览器标签页/会话合并去重；缺少覆盖回执时，活跃时间、容量价值与总体拥有成本均为无法估计。
- 主机容量清单（实现标识：`HostCapacityManifest`）签名固定 CPU、内存、NVMe 固态存储、部署位置与上限，只有推理依赖 A100；静态、最终、当前证明必须一致。数据、预写日志（实现标识：`WAL`）、临时文件、审计、活动、对象、评估、备份、交换空间的加密或密钥生成不符，或者出现明文或未获批的加密回退路径时，立即停止。
- 恢复点清单（实现标识：`RecoveryPointManifest`）是唯一 RPO 证据，原子绑定集群日志序列号/时间、应用/审计/评估高水位、叠加层、治理登记表、已消费账本、对象/评估检查点、密钥和候选身份；发布包（实现标识：`ReleaseBundle`）产生后、激活前必须生成发布包后清单。
- PostgreSQL 当前发布选择记录（实现标识：`ActiveReleaseSelection`）是当前发布的唯一权威数据源，当前发布镜像文件（实现标识：`current`）仅为镜像；替换只允许处于暂停状态（实现标识：`PAUSED`）并使用签名恢复 CAS，绝不盲目回退旧发布包。
- 顺序固定为初始签名前漏洞回执 → 全部非盲测、在线、浸泡和恢复门禁 → 盲测前回执 → 盲测评估 → 索引前回执 → 门禁索引（实现标识：`GateIndex`），三个回执都须验签，且最早有效截止时间（实现标识：`valid_until=min(advisory+24h, envelope expiry, earliest exception expiry)`）取安全公告期限、漏洞包过期时间和最早例外过期时间三者中的最小值。从基线期开始每日或早于最早有效截止时间重扫，持续覆盖过渡期、试点期和三个跟踪期。

## 1. 证据纪律

一个可讲的数字至少绑定：

```text
metric name + exact numerator/denominator
  + time window + population/slice
  + release/model/prompt/index/load manifest hashes
  + query/scorer version
  + raw artifact selector
```

统一规则：

- “0”只表示在明确测试集或观测窗口内观察为0；架构安全来自能力移除、鉴权、RLS和状态机，不来自零样本。
- 重复随机种子用于观察随机稳定性，不扩充独立样本量。
- 300例发布语料、420问检索隔离评测集、8小时负载运行和六周试点是四套不同证据，不能混分母。
- P50/P95/P99必须说明统计单位是事件、请求、线程还是分钟；平均到达率不能替代突发流量包络。
- 服务商接受、最终送达、已发送文件夹可见和投递状态通知（实现标识：`DSN`）是四种事实，不互相冒充。
- 租户保留期、RPO、RTO、令牌 TTL 等是该试点配置，不是产品硬编码默认值。

## 3. 冻结架构与试点环境

### 3.1 不变事实

| 维度 | 版本化口径 |
| --- | --- |
| 业务范围 | 1个企业租户、1个腾讯企业邮公共/共享邮箱（通过 IMAP/SMTP 访问的公共邮箱）、28名活跃企业微信用户 |
| 写入责任方 | 邮件命令网关 + 确定性工作流；模型无写工具 |
| RAG | Agent RAG MCP，通过认证且只读，三个工具；管理员摄取机械隔离 |
| 持久化权威数据 | PostgreSQL 16 + pgvector；Redis只做热缓存/信号 |
| 邮件 | IMAP 有界 UID 同步；SMTP DATA 栅栏；“投递结果不确定”是唯一表示模糊投递结果的枚举值 |
| 身份 | 租户企业标识（实现标识：`tenant_id=CorpID`）、操作者用户标识（实现标识：`actor_id=UserID`）；服务端 RBAC + 邮箱/资源/策略 |
| 主模型 | `Qwen/Qwen3.5-35B-A3B-GPTQ-Int4`，单张完整A100 40GB |
| 冷备 | `Qwen/Qwen3.5-9B` BF16；主模型完全卸载后才加载 |
| 检索 | BGE-M3 1024维 CPU + HNSW/FTS + RRF 参数60 + 同系列重排器 CPU |
| 网络 | 私有 Linux 系统；运行时模型互联网下载=0；外部 AI 出站=0 |
| 非目标 | GPU 高可用、多租户软件即服务、自动发送、图检索增强生成、微调、前端重设计 |

五人交付职责分工矩阵不是口头归功：架构/后端负责人直接负责事实边界、审批发送、RAG MCP契约与发布决策；其余四个主要负责人分别负责腾讯服务商/MIME、RAG摄取/检索、推理/评估、站点可靠性/质量保证/运维，每个域另有一名次要复核人/值班人。激活前职责分工与排班清单（实现标识：`deploy/pilot/manifests/current.json#staffing_plan_hash`）绑定职责分工矩阵和排班计划；六周每周清单索引（实现标识：`artifacts/pilot/current.json#weekly_manifest_hashes`）解析的各周不可变清单绑定实际值守交接、关键复核和批准记录，避免用启动快照“预知”未来。

试点租户策略第1版固定原始邮件/附件在线365天、受限提示词/输出排障窗口30天、审计元数据730天；法律保留优先于物理清除。这是该租户获批配置，不是产品声称的普遍法律期限；租户策略位置（实现标识：`deploy/pilot/manifests/current.json#tenant_policy`）记录当前版本和哈希，不另造策略版本指向记录。

## 4. 业务结果与统计口径

### 4.1 处理时长

| 指标 | 基线期 | 试点期 | 调整后分位数差 |
| --- | ---: | ---: | ---: |
| 处理时长 P50 | 12.4分钟 | 5.6分钟 | -6.8 [95%置信区间 -7.4, -6.1] |
| 处理时长 P90 | 31.2分钟 | 14.8分钟 | -16.4分钟 |
| 首次发送响应 P50 | 21分钟 | 7分钟 | -14.0 [95%置信区间 -16.2, -12.1] |
| 首次发送响应 P90 | 76分钟 | 29分钟 | -47分钟 |

主分析不是18,406个首个终态事件，而是两个独立42天窗口的主分析受理事件：人工且 AI 关闭的基线期 `30,880`、预固定非零≤24小时过渡期、试点期 `31,260`。每个已接受的入站事件在暴露前原子写入可处理性判定，取值为可处理事件、不可处理事件或待确认事件；只排除闭集不可处理事件，待确认事件保留，其可处理性分类保持为“待确认事件”，并强制人工且 AI 关闭。暂停、9B降级和AI全停仍留在试点分配中，窗口不顺延；恢复轮次只做写入栅栏，报告按激活证据链聚合所有轮次。试点结局分解为首个终态发送动作18,406、显式处理结论对应的人工/无需回复关闭7,660、策略阻断/转交2,384、7日右删失2,810，总和31,260；基线期对应18,497/7,310/2,230/2,843=30,880。业务字段缺失的基线期132/试点期174仍在ITT分母，以缺失指示变量、IPCW和预注册MNAR上下界处理；它不能替代单独的活动覆盖记录硬门。落在单侧细分层的基线期245/试点期312个观测值，按结果揭示前固定的父类别/受理排班组进行合并，不做依赖结果的删除。

标准化只使用处理事件暴露前字段：受理排班处理人、语言（中文、英文或混合）、确定性策略前类别和相对周次（第1至6周）。终态处理人、模型/策略产生的风险、是否形成草稿/进入复核/达到终态均禁止入权重。试点期权重为1，基线期按冻结的试点受理组合标准化。线程可跨处理人，置信区间采用受理处理人×客户线程的双向交叉鸽巢自助法：独立有放回抽样两类聚类，重复次数相乘；2,000次、随机种子=`20260712`，权重不在重采样内重估。P50/P90处理时长使用7日窗口的IPCW加权经验累积分布；观察性日历期比较仍不冒充随机实验因果。

IPCW删失模型同样只用受理排班处理人、语言、策略前类别、到达小时/星期、附件类别和相对周次；权重在预注册第1/第99百分位截尾。稳定权重均值基线期/试点期=`1.00/1.00`、最大值=`3.42/3.18`，倾向得分范围`0.14–0.86`，有效样本量=`28,940/30,880=93.7%`与`29,610/31,260=94.7%`。7日终态/删失模型综合布里尔分数=`0.082/0.076`、校准斜率=`0.98/1.01`。不截尾、第0.5/第99.5百分位和重叠加权三种敏感性中，处理时长P50差范围`-6.6至-7.0`，所有95%置信区间上界都<0。对174个非活动类业务字段缺失处理事件，相对于随机缺失（MAR）假设，施加 +20/+120/+600 分钟的处理时长差后，均值对比分别为`-3.44/-2.89/-0.22`分钟；转折点约`+638`分钟/缺失处理事件。它不允许填补活动覆盖记录的版本指向记录/证据链/角色覆盖缺口；该硬门失败时，活跃时间、容量价值和总体拥有成本直接判为无法估计。响应分析的保守+30分钟MNAR场景差为`-11.8`分钟、置信区间上界`-9.2`。因此结论不由少量大权重或常见业务字段缺失假设驱动，但仍不升级为随机因果。

首次发送响应有自己的预注册“受理时需要回复”分析队列，绝不复用首个终态分母：基线期适用20,140=SMTP接受16,980 + 竞争性非发送2,310 + 7日删失850；试点期适用20,380=接受17,950 + 竞争性事件1,810 + 删失620。21→7分钟及置信区间来自加权阿伦–约翰森接受子分布估计量（实现标识：`Aalen–Johansen`）；投递结果不确定、失败、已取消、策略/无需回复都不会被伪造为接受时间戳。

## 11. 二十个问题档案与事故复盘

分类说明：共20个问题档案，其中试点观测6个，是六周试点中的真实观测；门禁拦截6个，是发布门禁所拦截、未进入正式流量的问题；故障演练8个，是有意注入故障所得。面试时必须说清分类，不能把14个门禁拦截或故障演练包装成客户事故。

### 问题一 — 已有邮件的标记与EXPUNGE长期漂移

- **证据索引：** 问题一（实现标识：`INC-01`）；**证据分类：** 试点观测（实现标识：`PILOT`）。

- **信号：** 两名处理人报告，已在腾讯客户端移动或删除的邮件仍显示在收件箱；对账抽样发现17个位置不一致，涉及9个会话串。
- **根因：** 初版同步游标只扫描游标条件（实现标识：`UID > last_committed_uid`），却把标记与在箱状态当成已维护事实；IDLE也不会可靠通知所有既有UID变化。
- **止血：** 暂停把在箱状态用于自动工作流，对已配置文件夹的UID与标记做全量差异比对，并人工复核9个会话串。
- **长期修复：** 每30秒轮询新UID、每5分钟比对位置、每日盘点文件夹；EXPUNGE需终态证据或连续两轮一致才写入墓碑，QRESYNC只作可选优化。
- **结果：** 位置不一致17→0，权威邮件误删=0，位置收敛P95=6.2分钟。
- **反思：** “增量收新信”与“邮箱投影完整”是两个正确性合同。

### 问题二 — UIDVALIDITY重置叠加服务商限流

### 问题八 — 单PostgreSQL中断恢复后旧后台任务进程试图自动复活

- **证据索引：** 问题八（实现标识：`INC-08`）；**证据分类：** 故障演练（实现标识：`DRILL`）。

- **信号：** PostgreSQL不可用期间，后台任务进程和守卫进程被重启；数据库恢复后，持久试点激活状态仍为激活中，旧后台任务进程尝试领取并完成任务。
- **根因：** 早期演练只依赖数据库内CAS暂停，但数据库停机时无法写入暂停状态；若恢复后立即按激活状态启动，会越过新鲜的恢复授权。V1没有PostgreSQL高可用或新主库路径。
- **止血：** 由根用户拥有的权限恢复保持标志（实现标识：`AUTHORITY_RECOVERY_HOLD`）继续拒绝发送、扩展和AI任务领取；数据库恢复后先用签名CAS切到暂停状态，文件镜像不改变当前事实。
- **长期修复：** 每台可变更主机都部署只拒绝的守卫与锁存器；缺失或损坏也视为保持；只有新鲜预检与签名恢复产生新世代，并用CAS确认PostgreSQL当前发布选择记录后，才能清除全部锁存器。单库恢复继续遵循预写日志、备份和隔离恢复手册，不宣称具备仲裁、隔离旧主或盲目回退旧发布包的能力。
- **结果：** 数据库停机→后台任务进程/守卫重启→数据库恢复期间，发送、扩展和AI成功数=0、过期任务完成数=0、重复DATA=0；恢复后自动重放=0。
- **反思：** V1诚实选择单库恢复边界；没有选定高可用平台，就不能把“平台会隔离旧主”当成实测能力。

- **根因：** 把一个凭据的两种协议和信任链生命周期拆开处理。
- **止血：** 阻断切换，验证新密钥的IMAP和SMTP；先部署双信任包，再更换叶证书和证书颁发机构证书。
- **长期修复：** 采用“新凭据→双路探测→原子切换引用→排空→撤销”流程，并设置30/14/7天证书告警。
- **结果：** 撤销后使用旧引用=0、关闭证书校验（实现标识：`verify=False`）=0、轮换导致的生产中断=0。
- **反思：** 撤销后的旧密钥不可恢复，不能把它当作普通配置回滚。

### 问题十九 — 灾难恢复使待发送动作和已删除内容复活

- **证据索引：** 问题十九（实现标识：`INC-19`）；**证据分类：** 故障演练（实现标识：`DRILL`）。

- **信号：** 模拟备份截点后，SMTP已接受但数据库快照未记录；另有删除墓碑晚于每日全量备份。
- **根因：** 单独恢复PostgreSQL会遗漏外部副作用和跨存储删除水位。
- **止血：** 隔离恢复，启用恢复发送保持标志（实现标识：`RECOVERY_SEND_HOLD`），重放墓碑与审计记录，并扫描对象引用。
- **长期修复：** 每5分钟生成唯一恢复点清单，原子绑定同一集群的日志序列号（实现标识：`LSN`）和时间、应用/审计/评估高水位、叠加层、治理登记表、已消费账本、对象/评估检查点、密钥和候选身份，并在发布包生成后、激活前补充发布包后清单；持续复制对象，隔离所有非终态发送动作。
- **结果：** 有效恢复点时差为8分42秒、人工恢复时间为43分钟、恢复后的发送动作自动重放=0、已删除内容可被搜索到=0。
- **反思：** 数据库快照不能证明截点后SMTP没有接受。

### 问题二十 — 过宽高风险规则造成审批队列疲劳

- **证据索引：** 问题二十（实现标识：`INC-20`）；**证据分类：** 试点观测（实现标识：`PILOT`）。

- **信号：** 一个过宽的外部域原因码把审批队列P95推到26.4分钟，同类低风险案例重复升级；未发生错误发送。
- **根因：** 确定性规则把“外部域”单一条件当作高风险，没有结合收件人关系、附件和承诺字段，精确率下降。
- **止血：** 暂停该规则修订版的新发送授权，抽审近期动作并增加值班审批人；不降低高风险召回率硬门。
- **长期修复：** 在校准集上按原因码报告精确率和特异性，使用版本化租户策略收窄组合条件；授权复核API返回收件人、附件、证据和策略差异，供任意客户端使用，但本后端计划不修改前端。
- **结果：** 审批队列P95恢复到14.2分钟、总体精确率=96.1%、请求人自批=0。
- **反思：** 四眼机制若不监控人因，会退化成橡皮图章。

## 12. 高频算术与统计追问

### 12.1 漏斗分母

```text
review entry = 21,378 / 24,020 = 89.0%
first-terminal SendAction / AI-draft = 18,406 / 24,020 = 76.6%
```

简历中的“74%”不是第二个发送转化率，而是18,406个发送处理事件中的内容编辑分类。任何百分比都要先说明处理事件定义。

### 12.2 处理时长收益

```text
absolute median difference = 5.6 - 12.4 = -6.8 min
relative reduction = 6.8 / 12.4 = 54.8%
```

相对下降可说“约55%”，但优先报告绝对分钟和置信区间；P50置信区间来自完整主分析试点组（可处理事件加保留的待确认事件），经过暴露前标准化和IPCW后，对受理处理人×客户会话串做双向交叉自助法。不能用`6.8×终态样本数`估算总工时；只有活动覆盖记录（实现标识：`ActivityCoverageRecord`）完整通过时，容量总量才可使用31,260个主分析处理事件的逐事件活跃时间差：`111,104min=1,851.7h`，否则为无法估计（实现标识：`NOT_ESTIMABLE`）。

### 12.3 风险混淆矩阵

```text
recall      = 74 / (74 + 1)   = 98.7%
precision   = 74 / (74 + 3)   = 96.1%
specificity = 122 / (122 + 3) = 97.6%
```

只报召回率会允许“全部判为高风险”作弊；假阴性是安全代价，假阳性是审批疲劳代价，所以两类都必须保留。

### 12.4 RRF与重排增益

```text
RRF recall lift vs dense = (393 - 365) / 420 = +6.7 percentage points
NDCG absolute lift       = 0.887 - 0.812 = 0.075
relative NDCG lift       = 0.075 / 0.812 = 9.24%
```

NDCG以查询为单位做10,000次配对百分位自助法（随机种子=`20260712`）和100,000次配对随机化检验（+1修正），不把每个排序位置当作独立样本。

### 12.5 服务等级目标错误预算（SLO）

30天分钟数=`30×24×60=43,200`，本窗口排除数=`0`、不良数=`26`、良好数=`43,174`，观测值=`43,174/43,200=99.9398%→99.94%`。99.9%的连续预算是43.2分钟，但整数不良事件最多43个，所以剩余整数不良事件=17，第18个会违约；仍受14.4倍快速消耗、2倍慢速消耗和零容忍安全门约束。若预先批准的排除时长为 `E` 分钟，分母改为 `43,200-E`，预算改为 `0.001×(43,200-E)`，不能事后删除。

### 12.6 降级积压

```text
no new arrivals, same allowed mix: 64 / 0.62 ≈ 103 s
with same-mix 0.40 req/s arrivals: 64 / (0.62 - 0.40) ≈ 291 s
observed: 287 s
```

有效吞吐与到达率都来自同一个降级负载清单（摘要/分诊60%、草稿/RAG 40%，令牌与上下文分布相同）；否则上述请求速率减法无效，必须换成服务工作量单位。健康检查第#3轮的246秒就绪时间与287秒排空时间属于同一轮，因此总墙钟时间为533秒。就绪≤300秒与积压清空是两个SLO；若到达率≥有效吞吐，必须拒绝新请求或削减低优先级负载。

### 12.7 A100安全余量

最小安全余量按`(显存总量 - 峰值已提交或已使用包络) / 显存总量`计算，不能拿平均利用率替代。32K并发4的最差值12.1%通过≥10%门；64K并发2约4.7%失败，即使请求最终都返回也不通过。

### 12.8 “0事件”能说明什么

若把60个独立安全案例看成二项分布且观察值为0，粗略三倍法则上界约`3/60=5%`；把3个随机种子误当成180个独立样本而得到1.7%是不严谨的。更重要的是，攻击并非同分布随机样本，所以这里不应用统计话术替代能力移除和负向边界测试。

### 12.9 恢复点目标与恢复时间目标

恢复点目标直接检查恢复点时差条件（实现标识：`declared_failure_time - latest_verified_manifest.recovery_point_time<=900s`），同时验证所有数据库引用、审计高水位和密钥版本都存在于恢复域；不能只报告PostgreSQL预写日志或对象复制延迟。恢复时间目标从故障声明的第0时刻到特定能力恢复：查询/人工处理43分钟、同步57分钟、AI 61分钟；发送对账逐个动作完成，没有统一43分钟承诺。

### 12.10 MCP开销

数值比值`24/2160≈1.1%`只说明热协议量级远小于同一尾部试点组的端到端时间，不能当作可相加的P95或严格因果归因；同一试点组的关键路径跨度归因含73毫秒队列/序列化残差。仍不能忽略冷初始化P95为86毫秒、账本故障时默认拒绝，或CPU重排器1.82秒这一主瓶颈。

## 15. 一条坏草稿如何被完整重建

排障时不读取普通日志里的正文，而沿授权对象引用：

```text
handling_episode_id
  -> thread_id + inbound_version + assignment token
  -> RouteDecision + Router/source hash
  -> Profile/Prompt/Model/Runtime manifests
  -> ContextManifest (source/version/hash/token/packing)
  -> MCP AuthorizationContext receipt + jti/session fingerprint
  -> query + index_snapshot_id + EvidenceBundle hash
  -> RRF/rerank candidates + degradation
  -> ModelCall + structured validation/repair
  -> Draft version + deterministic Risk/Policy snapshots
  -> ReviewConfirmation / ApprovalGrant / SendAuthorization hash
  -> SendAction / Outbox / Job / ProviderAttempt / reconciliation
```

定位顺序：

1. 正确证据没进前80名/前20名：查索引新鲜度、ACL、分块、规范化器、稠密检索/FTS。
2. 正确证据已进证据包但回答错：查上下文装包、提示词/能力配置、结构校验/主张校验器。
3. 草稿正确但不能发：查风险/策略/披露、版本过期、角色/绑定。
4. 命令成功但服务商状态异常：查发送动作（实现标识：`SendAction`）、尝试阶段、网络包/数据库栅栏和已发送副本/投递状态通知。
5. 用户觉得“系统慢”：拆分队列、MCP、检索/重排、首个令牌延迟/逐输出令牌时间、审批和服务商，不只看总耗时。

## 17. 危险说法的精确替换

## 18. 残余风险与演进触发器

| 残余风险 | 当前补偿 | 触发下一架构决策 |
| --- | --- | --- |
| 单台A100构成AI单点故障 | 5分钟冷备 + 不依赖AI的邮件核心 | AI服务等级目标（SLO）/错误预算持续被单节点故障消耗 |
| 单个PostgreSQL主节点构成邮件核心单点故障 | 单集群预写日志 + 跨存储备份/恢复、恢复发送保持标志、权限恢复保持标志 | 一次数据库故障的恢复时间目标（RTO）或邮件核心错误预算证明恢复不足时，另立私有PostgreSQL高可用平台/仲裁/故障隔离架构决策记录与实测计划 |
| SMTP最终投递不可完全观测 | 接收状态与投递状态通知分离、不确定事件由人工对账 | 服务商提供可靠投递API或更换服务商 |
| 单租户未证明软件即服务运营 | 租户感知的数据模式与测试 | 第二个真实租户签约前 |
| 35万个分块未证明超大规模 | PostgreSQL/pgvector同一致性域 | 分块数/P95/垃圾回收/恢复连续越门 |
| CPU重排器是检索瓶颈 | 队列/降级契约 | P95/队列错误预算持续越门且有私有容量方案 |
| 人可误审批 | 绑定、差异、双人复核、审计 | 盲目批准/纠错越人因门，先改流程而非放松审批 |
| 直接用户邮箱名单回读依赖腾讯控制面 | 单对象非分页读取；精确28人，部门/标签为空；独立的仅服务商探针；新鲜度90秒，过期/未知时默认拒绝 | API/机制变化、无法维持仅直接用户或服务商探测失败 |
| 评测样本可能被长期过拟合 | 时间切分、去重；独立100例影子池每季度替换20个 | 漂移/线上错误超门或评估器变更 |
| 微调数据治理 | V1不训练 | ≥1,000对授权去标识样本且提示词/RAG改进饱和 |

## 19. 面试前最终自检

- 能在30秒、2分钟、5分钟三个长度讲清项目，并始终保持责任归属与数字一致。
- 每个比例都能说清分子、分母、统计单元、时间窗和是否为独立样本。
- 能画路由器→工具代理服务→MCP、审批→发送动作→SMTP、主路径→降级路径三条状态链。
- 能说明为什么不用通用自治智能体、直接RAG降级路径、自动重发、热备、图检索增强生成或微调。
- 能讲至少一个试点观测、一个门禁拦截和一个故障演练，不混淆真实性分类。
- 能解释一个失败结果，而不只背成功指标：风险漏判、四个拒答失败、64K、并发度2不通过、四次SMTP不确定事件。
- 能承认残余风险：单GPU、单个PostgreSQL主节点、SMTP可观测性、人因审批、单租户和授权服务失守。
- 能指出所有生产结论都绑定发布包；修改模型、提示词、分块、MCP工具结构定义或工作负载就要重评。
- 不声称现有学习版代码已经产生这些生产制品；本材料是已完成目标系统的统一演练口径。
