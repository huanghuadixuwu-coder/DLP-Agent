## 当前生产契约（本节优先）

> **训练优先级：** 下文题号和案例数字继续用于演练，但不得覆盖本节；这些是计划完成后的目标证据形状，不是当前学习版代码现状。

- 客户公共邮箱的一次完整、非分页 `publicmail/get` 必须返回精确 28 名直接用户，部门/标签为空；同应用另建仅服务商、仅探测探针邮箱，禁止客户内容、产品、IMAP 和发送，不进名单/试点组。客户名单始终只有这28人且不适用分页门。
- 业务日历是 42 天人工 AI 关闭基线期、预先固定的非零 ≤24h 过渡期、42 天试点期、三个独立 7 天跟踪期，汇总约 13 周就绪后加过渡期。三分类 `ActionabilityDecision` 只排除闭集 NON_ACTIONABLE；UNKNOWN 留在主分析并强制人工、AI 关闭。
- `ApprovalGrant` 与 `ApprovalDenial` 对同一请求互斥 CAS；拒绝不产生权限或新请求。非发送终态必须显式 `HandlingResolution`，`SEND_PENDING` 时阻断，禁止从界面、超时、标签或邮件状态推断。
- 企业微信只有新鲜 `status=1` 可授权（读取/变更 ≤60s，复核/审批/发送 ≤30s）。隐私安全 `ActivityInterval` 使用服务端时间，跨浏览器标签页/会话合并/去重；覆盖不完整则活跃时间/容量/总体拥有成本 为 `NOT_ESTIMABLE`。
- 签名 `HostCapacityManifest` 固定 CPU/内存/NVMe/部署位置/上限，只有推理依赖 A100；静态/最终/当前证明和数据/WAL/temp/审计/活动/对象/评估/备份/交换空间加密必须一致，明文/降级/漂移即停。
- 唯一 RPO 证据 `RecoveryPointManifest` 同时固定集群日志序列号/时间、应用/审计/评估高水位、叠加层、治理登记表、已消费账本、对象/评估检查点、密钥、候选项身份，并在包后、激活前补发布包后清单。
- 生效发布唯一真相是 PostgreSQL `ActiveReleaseSelection`，文件 `current` 只是镜像；替换仅能 `PAUSED` + 签名恢复 CAS，绝不盲回旧包。
- 顺序固定为初始签名前漏洞回执 → 全部非盲测/在线/浸泡/恢复门 → 盲测前回执 → 盲测 → 索引前回执 → GateIndex；`valid_until=min(advisory+24h, envelope expiry, earliest exception expiry)`，从基线期开始每日或更早于最早 valid_until 重扫，贯穿过渡期、试点期和三个跟踪期。

## 训练方法

每题练三档：

- 20 秒：只说结论和最关键机制。
- 60 秒：补充为什么、取舍和一个结果。
- 3 分钟：画数据流或状态机，讲一个故障案例，再说明边界。

回答统一使用五段式：

```text
业务/技术约束
  -> 架构决策
  -> 关键机制
  -> 代价与边界
  -> 评估或生产结果
```

如果面试官连续追问，不要不断堆组件名。回到“谁拥有事实、什么时候提交、失败后能否安全重试、用户下一步是什么”四个问题。

## A. 项目定位与总体架构

### 1. 这个项目解决了什么问题？

**60 秒主答**

共享邮箱的问题不只是回复慢，而是多人抢单、重复回复、知识口径不一致和高风险内容缺少责任人。普通 RAG Demo 只能回答问题，通用 Agent 又容易把概率输出直接连到真实副作用。我把它设计成硬邮件 Agent：同步、分配、草稿、风险、审批、发送和对账有确定性状态机；RAG MCP 提供只读证据；模型只生成候选。结果是人工处理时长中位数从 12.4 分钟降到 5.6 分钟；在版本化证据范围内，模型越权写入、模糊投递自动重放和确认重复发送都为 0。

**追问：为什么不用普通客服工单系统？**

工单系统擅长流转，但用户仍要手工读长线程、查知识和写回复。这个项目补的是证据检索、线程理解和草稿生产，同时保留工单式责任与审计。

**追问：你个人做了什么？**

我是 5 人小组的架构/后端负责人，直接权威责任方是事实所有权、审批/发送主链、RAG MCP 安全契约、A100 准入与分层评估。服务商适配/MIME、摄取和部署观测由其他成员主实现，我负责契约、关键代码审查、跨模块故障闭环和发布决策，避免把团队产出全部包装成个人编码；激活前职责矩阵/轮值计划由`deploy/pilot/manifests/current.json#staffing_plan_hash`绑定，实际每周交接/复核由`artifacts/pilot/current.json#weekly_manifest_hashes`绑定。

**危险说法**

不要说“RAG 自动处理邮件”或“AI 自动发信”。应说“AI 减少认知工作，服务端状态机控制副作用”。

### 2. 为什么称为硬邮件 Agent？

**60 秒主答**

“硬”指业务不变量由代码和持久状态强制，而不是靠提示词。身份来自企业微信，权限由服务端 RBAC/RLS 判断，风险由规则决定，审批绑定完整发送语义，SMTP 由唯一发送执行器执行。模型没有发送、审批、角色、凭据或记忆激活工具。它可以读、分析、检索和提出草稿，但不能把提案变成命令。

**追问：这会不会把 Agent 阉割成模板？**

不会。模型仍负责长线程摘要、分类信号、证据综合、个性化草稿和最多六步的只读规划。拿掉的是权威，不是推理能力。

**再追问：模型输出草稿算不算写操作？**

模型输出只是未持久授权的候选项。草稿写入必须由确定性工作流校验操作者、线程版本、结构定义和策略后执行。

### 3. 系统最核心的架构原则是什么？

**60 秒主答**

每类事实和副作用只有一个规范化权威责任方。邮件命令网关管业务写入，审批服务管确认和批准，发送执行器管 SMTP，RAG MCP 管证据，推理网关管模型路由，PostgreSQL 管持久真相。API、浏览器、模型、Redis 和旧辅助路径都不能成为第二权威责任方。这样权限、重试和降级不会在多个路径上漂移。

**追问：拆成微服务不就有权威责任方了吗？**

不一定。两个服务都持有 SMTP 凭据，或 API 和任务进程都能写发送状态，仍然是双权威责任方。所有权需要通过组合根、网络可达性、数据库角色、依赖注册和契约一起机械限制。

**危险说法**

不要把“模块很多”当作架构先进。重点是单一权威与禁止旁路。

### 4. 为什么是一个邮件 Agent 加一个 RAG MCP，而不是两个 Agent？

**60 秒主答**

邮件工作流需要跨状态、角色和外部副作用的一致性，必须有一个业务权威责任方。RAG 的职责是根据授权范围返回证据，不需要拥有自主目标，更不应参与邮件写入。把 RAG 做成只读 MCP 能独立演进检索栈，同时让邮件 Agent 只依赖证据包契约。两个自治 Agent 互相委派会引入权威不清、重试叠加和审计困难。

**追问：MCP 带来了什么实际价值？**

独立部署边界、最小工具表面、服务身份、mTLS、短期范围令牌、不同数据库角色，以及替换检索实现而不影响邮件业务。

生产传输使用内部 Streamable HTTP，便于统一 mTLS、会话绑定、限流与观测；stdio 只保留在 dev/测试，不进入生产环境组合。

**危险追问：MCP 协议本身安全吗？**

不。安全来自传输身份、授权令牌、重放守卫、ACL/RLS、只读凭证和网络隔离；MCP 只是能力契约。

### 5. 一次请求如何决定走哪个流程？

**60 秒主答**

唯一路由器分三类：确定性查询走 `DIRECT_READ`；草稿、分配、确认、审批、记忆审批和任何邮件变更走 `DETERMINISTIC_WORKFLOW`；复杂的只读分析走 `BOUNDED_ANALYSIS_PLAN`。规划器最多 6 步、8 次工具调用、依赖深度 3、3 个并行读、1 次重新规划、30 秒总时限，这些由代码预算而不是提示词强制。

**追问：为什么草稿也走确定性工作流？**

模型可以生成内容，但草稿属于版本化业务对象，会影响后续审批。持久化时必须验证操作者、认领、线程版本、结构定义和证据来源信息。

**危险追问：能不能给规划器一个发送工具，最后让用户确认？**

不能。工具可见性本身就扩大攻击面；规划器只生成提案，确认后由新的确定性命令重新授权和执行。

### 6. 为什么 AI 全挂时还要能发送邮件？

**60 秒主答**

企业邮箱是业务基础设施，模型是增强能力，不能把二者的可用性绑死。IMAP 同步、人工草稿、风险规则、复核/审批、发送动作、SMTP 和对账都不依赖 LLM。模型或 RAG 故障只影响摘要、检索和智能草稿，并返回类型化降级。如果租户策略要求某类回复必须有证据，RAG 故障会明确拒绝，而不是伪造证据。

**追问：那为什么还叫 Agent？**

Agent 负责感知邮件、组织证据、提出计划和草稿；但执行权受业务内核约束。这是可用的企业 Agent，而不是自治程度竞赛。

**边界**

AI 全挂不是“用户无感”。用户会失去智能能力，但核心邮件工作不停止。

## B. 身份、授权与持久化

### 7. 企业微信登录后为什么还要每个命令重新鉴权？

**60 秒主答**

登录只证明某个时刻的身份。每次操作检查已认证操作者→新鲜企业微信成员状态→租户 成员关系→角色→邮箱绑定→资源→策略；只有 `status=1` 可授权，读取/变更证据时效≤60秒，复核/审批/发送栅栏≤30秒，未知/过期/刷新失败均默认拒绝。客户公共邮箱只允许一次完整、非分页 `publicmail/get`：`userid_list` 精确等于28名符合条件直接用户，部门/标签为空；额外/缺失、应用可见范围丢失、未知或时效>90秒都 `mailbox_membership_unverified`。同应用的仅服务商、仅探测探针是另一个邮箱，只做控制面探测，不含客户内容，也不进产品、IMAP、发送、roster 或业务分母。

**追问：为什么不能把角色放进长期 JWT？**

长 JWT 会让撤权在过期前无法生效。交互端使用不透明服务端会话，权威角色从服务端读取；内部短期令牌只承载被服务端计算的最小范围。

**危险说法**

邮件 From、用户邮箱、显示名和请求请求头都不是身份来源。

### 8. 只有一个租户，为什么从第一天做具备租户边界？

**60 秒主答**

身份、数据主键和授权后补 tenant_id 的迁移风险最大，所以结构定义、对象 键、缓存 键、MCP 会话、ACL 和审计从第一天带 租户 范围。V1 实际只部署一个企业租户和一个邮箱，没有提前建设计费、注册或多区域 SaaS。它是“安全边界多租户化，产品范围单租户化”。

**追问：如何证明不是只靠 where tenant_id？**

应用授权、PostgreSQL RLS、MCP 令牌范围、实时文档 ACL、租户对象前缀和短期对象凭据多层独立强制。

**危险说法**

不要说已大规模多租户商用；说单租户试点、具备租户边界架构。

### 9. PostgreSQL 为什么是唯一业务真相？

**60 秒主答**

因为一次命令通常同时改变聚合状态、版本、审计事件和后续异步任务。PostgreSQL 事务可以把 reauthorization、CAS、领域事件、发件箱事务记录和幂等原子提交。Redis、消息队列或进程锁无法同时提供这些语义。数据库服务端时间和租约令牌还可以阻止过期任务进程完成新权威责任方的任务。

**追问：PostgreSQL 会成为瓶颈吗？**

V1 单邮箱吞吐很低，正确性比极端 QPS 重要。读侧可以做投影、索引和非权威缓存；将来可分区或拆服务，但业务提交的权威仍需明确。

**再追问：为什么不用 Kafka 做事件来源？**

V1 不需要引入第二个一致性域。PostgreSQL 仅追加领域事件足以审计，发件箱事务记录再可靠传播异步工作。

### 10. Redis 到底做什么？

**60 秒主答**

Redis 只保存可重建的热缓存、短期投影和任务进程唤醒信号。它不保存角色、认领真相、审批、幂等、任务租约、MCP 重放或发送状态。Redis 不可用时查询回源 PostgreSQL，任务进程通过持久轮询恢复；性能会下降，但授权和正确性不变。

**追问：敏感限流能否用 Redis？**

可以用于快速计数，但安全边界必须默认拒绝或有 PostgreSQL 权威路径，不能因 Redis 丢 键 自动放宽权限。

**危险说法**

不要说“Redis 宕机完全无影响”；正确说法是无正确性影响，但有延迟和数据库压力影响。

### 11. 发件箱事务记录解决了什么，没有解决什么？

**60 秒主答**

发件箱事务记录解决业务状态提交和异步意图发布之间的双写：同一事务创建发送动作、领域事件和不可变发件箱事务记录，物化进程再幂等生成 Job。它保证一个已消费授权只有一个逻辑发送工作，但不保证外部 SMTP 恰好一次，也不证明最终投递。

**追问：重复命令怎么办？**

以 `(tenant_id, command_type, client_request_id)` 做幂等键，重复命令返回同一回执；一次授权只能 CAS 消费一次。

**危险追问：有了唯一约束，为什么还会重复邮件？**

数据库唯一性只覆盖本地意图。网络断线时远端可能已接收，客户端却不知道，因此还需要 DATA 栅栏和 `DELIVERY_UNCERTAIN`。

### 12. 两个任务进程如何安全竞争任务？

**60 秒主答**

任务进程使用 `SKIP LOCKED` 领取 Job，PostgreSQL 服务端时间计算租约，随机租约令牌作为防护栅栏令牌。renew、完整、失败都必须匹配当前令牌和版本。租约过期后新任务进程可以接管重放-safe 工作，旧任务进程即使复活也更新不到一行。

**追问：所有任务都能接管吗？**

不能。发送任务一旦进入或可能进入 SMTP DATA，就不是普通重放-safe 任务，必须转入不确定性对账，不能由新任务进程重放。

**危险说法**

不要只说“分布式锁”。要说明权限、服务端时间、令牌和副作用边界。

## C. IMAP 同步、邮件身份与共享协作

### 13. IMAP 增量同步怎样避免漏信？

**60 秒主答**

每轮在同一个已选择-文件夹会话中获取 `UIDVALIDITY` 和 `UIDNEXT`，固定 `upper=UIDNEXT-1`，按 UID 升序分页。只有本轮返回的 UID 全部被持久化或有明确终态记录后，游标才推进。新到邮件若 UID 大于上界，留给下一轮；UID 空洞是合法的，不能把空洞当漏信。

**追问：为什么不用时间戳？**

日期受时区、服务器索引和边界重叠影响；序列 number 会因删除变化；UID 才是选定 UIDVALIDITY 命名空间内的稳定位置。

**再追问：IDLE 呢？**

IDLE 只降低延迟，可能断线或漏通知；轮询/对账才是正确性基线期。

### 14. UIDVALIDITY 变化怎么办？

**60 秒主答**

UIDVALIDITY 变化表示 UID 命名空间被重建，旧 `last_uid` 完全失去语义。系统不会继续增量，而是对配置的完整保留期时间范围重扫，用服务商位置、原始内容/正文哈希和 RFC 信息去重，同时为新文件夹位置建记录。更老且无法证明完整的历史进入后台对账，不能宣称已同步完整。

**追问：重扫是不是很慢？**

会增加临时负载，但它是罕见恢复路径，可以有界分页和后台执行。正确性优先于假装秒级恢复。

**危险说法**

Message-ID 只辅助去重，不能替代服务商身份。

### 15. 任务进程在一页同步中间崩溃怎么办？

**60 秒主答**

原始对象写入是内容-已处理幂等操作；消息投影、位置、事件和游标推进在原子边界提交。若任务进程在提交前崩溃，下次会重复拉取和写入，但不会重复业务对象；若提交后崩溃，游标已与消息一起生效。不能先移动游标再写消息。

**追问：对象存储写成功但 DB 失败呢？**

可能留下无引用二进制对象，由生命周期清理；不能反过来让 DB 宣称有一个不存在的对象。持久投影只在对象哈希已确认后提交。

### 16. 为什么邮件记录和邮件位置记录分开？

**60 秒主答**

同一封逻辑邮件可能同时存在 Inbox、Sent 或 Archive，不同文件夹各有 UID、标志和 InternalDate。`MailMessage` 保存规范化内容，`MailMessageLocation` 保存 `(mailbox, folder, UIDVALIDITY, UID)` 的服务商位置。跨文件夹去重是把多个位置关联到一条内容，不是覆盖或删除位置事实。

**追问：Message-ID 是主键吗？**

不是。它来自外部、可能缺失、重复或伪造；只能作为 RFC 线程关联和去重证据。

### 17. 线程如何归并，怎样防止串客户？

**60 秒主答**

唯一可解析的`In-Reply-To`或`References`最右唯一父节点都只是候选项。自动link还必须同时满足同租户/邮箱、精确版本化`CustomerBoundaryRegistry`兼容、participant/收件人连续，以及确定性`trusted_ingress_auth=PASS`（受信服务商 DMARC PASS，或本地以对齐 DKIM/SPF重算DMARC PASS）。原始内容/转发 `Authentication-Results`、同域、subject和时间相似度都不能升级权限；任何未知/失败/冲突/环/多候选进入`ThreadLinkConflict`，且不继承认领、审批、证据、记忆或回复受众。

**追问：这样会不会降低自动归并率？**

会有少量人工冲突，但线程误合并会把另一个客户的证据、审批和回复带过来，错误半径远大于人工确认成本。

**危险说法**

不要说“同主题就是同线程”。

### 18. 两个处理人同时认领一个线程怎么办？

**60 秒主答**

认领是 PostgreSQL 聚合命令，使用预期版本和认领租约 CAS。默认租约 15 分钟，活跃时每 5 分钟续约；两个并发请求只有一个能提交。草稿更新也必须持有有效认领令牌和正确线程/草稿版本，拒绝 last-写入-wins。

**追问：为什么不用实时多人协同？**

V1 的业务目标是一个明确责任人，不是多人共编。需要协作时可以转派或评论；CRDT 会增加责任和审批语义复杂度。

### 19. 新来信为什么会让旧草稿失效？

**60 秒主答**

新来信可能改变客户意图、金额、附件或约束。线程版本增加后，基于旧版本生成和确认的草稿变为过期；发送提交的 CAS 会失败。处理人必须 rebase 或重生成，然后重新确认/审批。

**追问：客户只说了“谢谢”也要失效吗？**

系统不能安全地让模型判断新内容“无关”并复用授权。可以把 rebase 体验做轻，但不能绕过版本绑定。

**危险说法**

不要说系统自动 merge 后沿用审批。

## D. 草稿、审批、发送与对账

### 20. 普通、高、严重如何处理？

**60 秒主答**

风险最终由确定性规则和版本化租户策略决定，模型只给候选信号。普通由拥有线程的处理人给 `ReviewConfirmation`；高由处理人发起，另一个审批人对同一请求用互斥 CAS 给 `ApprovalGrant` 或 `ApprovalDenial`；拒绝不授权，也不隐式创建新请求。严重直接阻断，任何角色都不能批准绕过。外部域、敏感附件、金额/承诺等是策略输入，具体判为高还是严重由租户策略决定；降级草稿固定提升为高。若处理事件不发送，处理人必须显式提交 `HandlingResolution`；`SEND_PENDING` 时阻断，不能从界面/超时/标签推断。

**追问：为什么普通可以自己确认？**

这是业务责任确认，不是高风险自审批。若全部邮件都四眼审批，审批队列会成为瓶颈，用户会绕开系统。

**危险追问：MailAdmin 能否特批严重？**

不能。MailAdmin 管配置，不天然获得审批人权限，更不能越过严重策略。

### 21. 审批通过记录精确批准了什么？

**60 秒主答**

它批准的是规范化后的完整发送语义：租户/邮箱、线程/草稿版本、requester/审批人、发件人/回复地址/收件人/抄送、SMTP MAIL FROM、完整 RCPT 含 Bcc、主题、规范化正文、回复请求头、CID/MIME、附件顺序与哈希、证据包、风险/策略快照、动作 ID、issued_at 和过期时间。为避免哈希自引用，使用 `BoundPreimageV1={binding_schema_version,payload_without_preview_hash}`，计算 `preview_hash=SHA-256(JCS(BoundPreimageV1))`，最终邮件信封再携带 preimage 与 preview_hash。

同一审批请求的拒绝与授权共享版本/栅栏并互斥；`ApprovalDenial` 只留下拒绝证据，不是负向授权，也不会替处理人生成新的请求或 `HandlingResolution`。

**追问：为什么 Bcc 也必须绑定？**

Bcc 不在可见请求头，但是真实邮件信封的收件人，若不绑定就能在审批后偷偷增加接收者。

**再追问：MIME 边界会变化怎么办？**

Date 和边界是明确排除的传输派生字段，但不得改变已批准语义；任务进程使用不可变规范化内容生成。

**追问：JCS JSON 和最终 SMTP 字节之间会不会有缝？**

地址、Unicode、HTML、CID、附件顺序和邮件组展开都有版本化规范化规则；组 收件人 在审批前展开，不能发送时动态变化。确定性 MIME 渲染器版本随 ReleaseBundle 固定，最终 MIME 字节和 SHA-256 持久化到发件箱事务记录。渲染器升级若会改变语义，旧授权必须失效。

### 22. 为什么审批请求和发送授权分开？

**60 秒主答**

审批可以有较长业务处理窗口，默认 24 小时；真正发送前还要重新验证操作者、版本和策略，因此生成一次性、默认 5 分钟的 SendAuthorization。发送提交原子消费它并创建不可变发送动作。这样既支持异步审批，又缩小审批到副作用之间的 TOCTOU 窗口。

**追问：授权过期后能否刷新？**

不能刷新。旧确认/批准也不再可用；必须按当前版本和策略重新创建 `ReviewConfirmation` 或 `ApprovalGrant`，再签发新的五分钟授权。

**危险说法**

界面的 `confirmed=true` 或自然语言“同意发送”都没有授权价值。

### 23. 为什么策略要检查两次？

**60 秒主答**

第一次在创建确认/审批前，帮助用户修正 DLP、收件人 领域、附件和风险问题；第二次在 SMTP 前，对不可变已认领载荷和当前 租户 策略再检查，防止审批期间策略、凭据、收件人或内容发生变化。第二次失败不执行 SMTP，终态取消已认领发送动作，并使绑定的 `ReviewConfirmation`、`ApprovalGrant` 和 `SendAuthorization` 全部失效；必须重新复核/审批，不能重试旧动作。

**追问：既然哈希没变，为什么策略还会变？**

租户策略、禁发域、用户权限、凭据状态和服务商成员关系都可能变化，哈希只证明载荷没变。

### 24. 发送动作、发件箱事务记录、Job、服务商发送尝试分别是什么？

**60 秒主答**

- `SendAction`：一次经过授权的业务发送意图，固定 Message-ID 和完整语义。
- `Outbox`：同事务生成的不可变执行载荷。
- `Job`：可租约调度的异步工作载体。
- `ProviderAttempt`：一次 SMTP 协议尝试的阶段证据。

一个授权对应一个发送动作、一个发件箱事务记录、一个逻辑 Job。DATA 前只有在旧任务进程已被 fenced、旧 SMTP 事务被持久证明关闭时才允许重新建立会话；硬约束是每个发送动作的 `DATA_STARTED` 计数 ≤1。`ProviderAttempt` 的物理记录基数以已发布结构定义为准，不能用记录行数代替副作用不变量。

**危险说法**

不要用 `ProviderAttempt` 行数承诺恰好一次；应说“每个发送动作的 `DATA_STARTED` 计数 ≤1，且 DATA 前重连有持久关闭证据”。

### 25. 为什么不能保证邮件恰好一次？

**60 秒主答**

SMTP 服务端可能已接受 DATA，但客户端在收到最终响应前断线。本地事务和幂等键无法查询远端的原子真相，腾讯 服务商也不提供 idempotent-发送 键。因此我们只承诺：一个发送动作最多一次进入 DATA；任何可能已接受的异常进入 `DELIVERY_UNCERTAIN`，不自动重试，使用 Message-ID、Sent 与持久服务商发送尝试/服务商证据对账；DSN/退信单独记录为 `DeliveryObservation`。

**追问：稳定 Message-ID 不能去重吗？**

Message-ID 是追踪和对账标识，不是 SMTP 服务商的幂等键，不能假设服务器会拒绝同 Message-ID。

**危险追问：不重试会降低可用性吗？**

会把少量事件转为人工处理，但重复报价或承诺的业务损失更大。这是显式风险选择。

### 26. `DATA_STARTED` 为什么是重试边界？

**60 秒主答**

在 DATA 前，如果能证明旧会话已关闭且没有进入消息传输，可以安全地重建连接；一旦进入或可能进入 DATA，远端可能已持久化整封邮件。发送执行器在传输前以租约 CAS 持久化 `DATA_STARTED`，因此新任务进程看到这个状态不会执行 SMTP，而是进入对账。

**追问：最终 250 后进程崩溃呢？**

即使本地尚未记录最终，也属于可能已接受，仍进入不确定状态。后续用服务商证据修正观察结果，绝不重放旧 Action。

### 27. `SENT` 和“已送达”有什么区别？

**60 秒主答**

`SENT` 仅表示配置的腾讯外发 SMTP 返回明确接受，证明它接收了责任，不证明每个终端收件人收到。Sent 文件夹是对账证据；DSN/退信是独立 `DeliveryObservation`。二者都不证明最终送达，DSN/退信不改写 SMTP 接受事实。对用户展示时要区分“服务器已接受”“投递失败通知”和“投递状态不确定”。

**追问：为什么不直接显示已发送？**

可以显示“已提交到邮件服务器”，但不能用文案掩盖协议边界；高风险业务尤其需要准确语义。

### 28. 部分 RCPT 接受、部分拒绝怎么办？

**60 秒主答**

在进入 DATA 前收集所有批准收件人的 RCPT 响应。如果任何已批准的收件人/抄送/密送 收件人 被拒绝，系统 RSET/关闭，不发送给剩余部分，因为“只发给部分人”改变了被审批的 收件人 语义。用户修正地址后重新走确认或审批。

**追问：这不是牺牲可用性吗？**

是有意选择一致的业务语义。系统不能替用户决定哪些人可以缺席一封已审批邮件。

### 29. `DELIVERY_UNCERTAIN` 怎样闭环？

**60 秒主答**

Reconciler 先按稳定 Message-ID 查询经过能力探测的 Sent 文件夹，再结合持久服务商发送尝试/服务商证据，输出 `CONFIRMED_ACCEPTED`、`CONFIRMED_NOT_DISPATCHED` 或 `STILL_UNCERTAIN`。Sent 中找不到不能证明未发送。DSN/退信只记录为独立 `DeliveryObservation`，不改写 SMTP 接受事实。若仍不确定，只有人可以决定创建全新授权、新发送动作和新 Message-ID；旧动作永不重放。

**危险说法**

不要说“人工点重试旧任务”，而是“人工授权一个有审计关联的替换动作”。

### 30. 灾备恢复后待处理发送能否继续？

**60 秒主答**

不能自动继续。数据库快照只反映截点前本地状态，截点后 SMTP 可能已经接受邮件。恢复环境进入 `RECOVERY_SEND_HOLD`，所有非终态发送动作隔离，无论快照里看似是否 DATA 前。先做服务商对账，只有重放-safe 的非发送 Job 可恢复；需要重发时创建新授权和新 Action。

**追问：这会影响 RTO 吗？**

会让发送恢复比查询更保守，但把外部副作用纳入灾备语义比单纯追求快速重启更重要。

## E. RAG MCP、检索与证据

### 31. RAG MCP 为什么只暴露三个工具？

**60 秒主答**

模型只需要 `search_evidence`、`get_evidence` 和 `get_document_metadata`。上传、摄取、reindex、删除、任意知识集合和配置工具属于管理面，使用不同服务身份、端点、网络策略、DB 角色、对象凭据和组合根。最小登记表降低提示词注入可以触达的能力，但真正安全仍依赖基础设施隔离。

**追问：只隐藏写工具够吗？**

不够。Agent 进程不加载写 处理人、不持有写数据库身份，管理端拒绝代理服务受众，网络也不可达。

### 32. 工具代理服务和 MCP 为什么都要鉴权？

**60 秒主答**

代理服务根据当前邮件 Agent 操作者/资源计算最小知识范围，签发短期令牌；MCP 不能盲信代理服务，还要验证 mTLS、签发者、受众、过期时间、jti、租户、操作者、范围和实时 ACL。两层独立强制可以防止调用方参数注入、代理服务配置错误和跨范围 ID 访问。

**追问：模型能传 租户 或知识集合过滤吗？**

不能。只允许来源 type、date 范围等非权威过滤；租户、范围、ACL、知识集合和路径由服务端注入。

### 33. MCP 令牌如何防重放？

**60 秒主答**

短期令牌固定 `iss/aud/exp/jti/tenant/actor/scope`。PostgreSQL TokenReplayGuard 首次使用时原子绑定 `jti + claims_hash` 到 MCP 会话指纹，之后只允许同一绑定。Redis 不能保存这个安全真相；账本不可用时 MCP 认证默认拒绝。

**追问：为什么允许同一会话后续调用？**

Streamable HTTP 会话需要多次工具交互，所以防的是换会话/声明的重放，不是一次令牌只能发一个 HTTP 请求。

### 34. 为什么用 pgvector + FTS + RRF + Cross-Encoder？

**60 秒主答**

Dense 处理语义改写，FTS 保留产品名、订单号、法规编号等精确实体；RRF 在不同分数空间中稳定融合；Cross-Encoder 对 top 候选项做查询-文档联合精排。盲测 隔离评测中标准可回答 Recall@20从 FTS 79.2%、稠密检索 88.9%提升到RRF 95.8%；含60个无答案空集判定的标准答案-结果 成功分别为79.8%/86.9%/93.6%；360个相关性-bearing 查询上的NDCG@10从0.812提升到0.887。

**追问：为什么不用加权分数直接相加？**

两路分数分布和校准不同，RRF 对尺度不敏感、调参更稳。后续若有足够标注可以学习融合，但 V1 优先可解释和稳定。

### 35. 为什么生产用 PostgreSQL，不用专用向量库？

**60 秒主答**

当前约 35 万文本块，性能不是首要矛盾；权限、版本、删除和审计才是。PostgreSQL 让 DocumentVersion、ACL、删除状态、FTS 和向量处于同一一致性域，并可使用 RLS。未来规模或 P95 越过明确阈值时，可在 MCP 契约后替换检索存储，不改变邮件 Agent。

**追问：什么时候会拆？**

持续观察文本块数、索引构建/清理、检索 P95、租户 noisy-neighbor 和恢复时间；不能只因“专用库更专业”就提前增加一致性域。

### 36. 证据包为什么不是一组字符串？

**60 秒主答**

它记录查询、范围、文档与不可变版本、文本块定位信息、内容哈希、检索方法/scores、ACL/索引快照、去重决策、时间戳、降级和包哈希。这样能回答某封草稿基于什么版本、为什么选中、权限当时如何，并在审批绑定中冻结证据语义。

**追问：证据内容可信吗？**

内容统一标记 `untrusted_evidence`。它可以支持主张，但不能提供身份、权限、批准、记忆激活或发送指令。

### 37. 已知 evidence_id 为什么还要重新查 ACL？

**60 秒主答**

不透明 ID 不是能力。文档可能在令牌签发后撤权、删除或换范围，每次 获取-by-id 都用当前 MCP 会话和最新 ACL 重验；数据库角色/RLS 再做底层隔离。因此猜中或从旧日志获得 ID 也不能读取。

**危险追问：UUID 很难猜，是否过度设计？**

泄漏 ID 的渠道很多，安全不能建立在概率不可猜上。重新授权成本小，避免的是跨客户数据泄漏。

### 38. 重排器宕机和 RAG 全挂有什么区别？

**60 秒主答**

重排器不可用时稠密检索/FTS/RRF 已有候选，可以返回融合排序，并显式标记 `retrieval_degraded=reranker_unavailable`；已知 NDCG@10 会从约 0.887 降到 0.812。稠密检索和 FTS 都不可用时返回 `evidence_unavailable`，不调用外部服务、不用 LLM 重排，也不直接 import/Chroma 兜底。

**追问：为什么不静默降级？**

高风险策略和用户下一步依赖证据质量。隐藏退化会让低质量结果看起来和正常结果一样可信。

### 39. 如何处理相互冲突的证据？

**60 秒主答**

检索不应简单挑一个最流畅版本。DocumentVersion、生效/删除元数据和来源信息随结果返回；证据包保留冲突项，RAG 综合明确指出差异、优先有效版本，无法判定时拒答或请求人工选择。冲突本身进入反馈数据，用于索引版本和标注修复。

**危险说法**

不要说“让大模型判断哪个是真的”。模型可以解释，权威取决于版本、来源和业务规则。

### 40. 如何防 RAG 提示词注入？

**60 秒主答**

先把所有证据标为不可信，分隔数据和指令；再从能力层保证模型只有只读工具，没有范围、审批或发送权；RAG MCP 对调用方参数、ID 和 ACL 重验；附件在 无出站沙箱清洗。间接外泄由 AuthorizationService 独占授权真相的 `EvidenceDisclosurePolicy` 控制：生效 TenantPolicy 和 `DocumentVersion` 只拒绝分类是输入，证据包固定全部提供给模型的 EvidenceItem；Mail Policy Engine 只是强制执行适配器，在 前复核/发送前两次对整个包与完整收件人/抄送/密送 RCPT 计算约束，不依赖模型引用。缺失/未知默认拒绝，规则只能收窄、不能授予 收件人 权限，标签/策略变化使旧授权过期；引用检查和输出 DLP 只做补充。60 个案例覆盖直接指令、编码、改写/聚合、同域跨客户、隐藏文本、删引用六类并运行 3 随机种子，可提交密钥数据外泄为 0，但候选内容仍需人审。

**追问：还需要提示词防护吗？**

需要用于减少输出污染和提高拒答，但它是内容质量防线，不是授权防线。

## F. 私有推理、上下文、记忆与附件

### 41. 为什么选 `Qwen/Qwen3.5-35B-A3B-GPTQ-Int4`？

**60 秒主答**

约束是一张 A100 40GB、私有多模态、双语邮件、结构化输出和可接受延迟。`Qwen/Qwen3.5-35B-A3B-GPTQ-Int4` 的生效参数和 Int4 权重在单卡上提供了比 `Qwen/Qwen3.5-9B` 更好的长线程、草稿和视觉能力，同时保留 KV 缓存空间。最终不是凭参数推断，而是用清单-pinned 32K/64K、并发和视觉矩阵证明准入。

**追问：量化会损失质量吗？**

会，所以同一量化证据产物、分词器、提示词/能力配置进入 300-案例评估。若关键事实、风险或结构化输出不过门，就不能因为性能好而发布。

**危险说法**

不要宣称模型“天然适合”或仅凭基准测试选择；强调业务案例与容量共同决策。

### 42. 单 A100 的批准容量是多少？

**60 秒主答**

LoadManifest 放行正常 32K 文本并发 4、例外 64K 文本并发 1、视觉单请求最多 4 图且降低文本并发。64K c2 虽有请求完成，但显存余量和队列斜率未过门，因此标为 UNSAFE。8 小时混合负载最低显存余量约 12%，OOM 和已接受-任务丢失均为 0。

这个结论只绑定到明确邮件信封：每个8小时运行 9,600请求，随机种子=`401/402/403`；每小时300秒突发放165 请求，8小时1,320，其余26,400秒放8,280，所以基础=0.313636 请求/秒、总体=0.333333 请求/秒。输入 P50/P95 4.1K/28K 令牌，输出 P50/P95 420/1.2K，64K 案例约2%。三个完整运行取最差值，队列 P99 1.9秒、草稿/RAG P99 29.4秒、视觉 P99 58.7秒，最大队列深度7。

生产AI 到达按UTC对齐、无重叠300秒时间桶统计：P95=`63/300=0.21`、P99=`102/300=0.34`、最大=`123/300=0.41 req/s`；0.55 突发约为P99的1.6倍。9B 已降级 组合固定摘要/triage60%、草稿/RAG40%及同一令牌/上下文分布，goodput0.62与arrival0.40同质，才能算net0.22。健康检查运行 #3 就绪=246秒，同一运行 84到达/64 已接受/20 `MODEL_SWITCHING`，积压实测287秒，触发→清除=533秒；无新到达约103秒。丢失 已接受=0。

**追问：支持 64K 为什么不默认使用？**

更长上下文增加 KV 缓存、尾延迟和噪声。正常能力配置用 32K，只有摘要后仍保留大量必选事实的长线程才进入 64K 准入。

### 43. Phase 0 如何避免“压测跑着跑着自动降并发作弊”？

**60 秒主答**

候选 Model/能力配置/Load 清单在运行前冻结并哈希；执行进程只能采集，评估器只能判定，发布者只在全部门禁通过后原子激活。某个单元失败只能标 UNSAFE 或停止架构评审，不能在同一次运行中修改上下文、并发、模型或视觉范围。

**追问：为何要不可变证据包？**

否则无法区分结果来自哪个来源提交、模型修订、vLLM 图像、驱动、提示词或工作负载，容量结论不可复现。

### 44. 主模型故障后如何切到 9B？

**60 秒主答**

一次进程 exit/OOM，或 30 秒内连续三次健康失败会熔断。网关先用上次已知良好、32K/c1 安全重启一次；再次失败则确认主 PID 消失、显存归零，再加载 9B。摘要、分诊、草稿、RAG 综合冒烟测试全通过、规划器/视觉/记忆负向校验通过，并且绑定当前 Phase 8 四能力配置降级-评估清单哈希，才进入 `DEGRADED`。三类故障分别约 214、231、246 秒就绪。

**追问：为什么不自动切回主模型？**

避免反复抖动。由运维人员启动至少 20 个代表性探针和 10 分钟稳定观察，再激活主模型。

### 45. 9B 降级为什么要减少能力？

**60 秒主答**

降级模型在复杂规划、视觉和长期记忆判断上没有达到同一质量边界，所以不是“接口兼容就全开”。只允许摘要、分诊、RAG 综合和草稿；草稿强制高风险，必须独立审批。能力缩减写进 ProfileManifest，不由调用方或提示词临时决定。

**危险追问：能否让 9B 先规划，人工看一下？**

当前发布契约明确禁止。要开放必须有新的能力配置评估与发布，不在事故中临时扩权。

### 46. 长线程如何避免把关键状态摘要丢掉？

**60 秒主答**

使用当前模型清单的精确 分词器 计算输入预算；70% 时生成有来源信息的 versioned 摘要，85% 时硬性上下文装箱。系统策略、当前请求、待处理动作、审批哈希、最新线程事实、工具 结果 和降级状态是 mandatory，结构化对象不从中间截断。如果 mandatory 本身超预算，返回 `CONTEXT_OVERFLOW`。

**追问：摘要错了怎么办？**

摘要是 CAS 更新的派生投影，不是事实源。ContextManifest 记录每个来源/版本/哈希/令牌/装箱决策，可回到仅追加事件和原始邮件重建。

### 47. 为什么外部邮件不能自动成为长期记忆？

**60 秒主答**

否则任意发件人可以通过一封邮件永久改变系统偏好或业务事实。外部内容、RAG 和模型只能创建 `MemoryCandidate`，带范围、来源信息、证据、置信度、TTL 和冲突 键。操作者范围由授权处理人处理，邮箱/租户 范围需 MailAdmin；外部来源且影响多人时 proposer 与审批人分离。

**追问：哪些内容永远不能进记忆？**

身份、租户、邮箱绑定、收件人 邮件信封、权限、审批真相和投递真相。

### 48. 附件与多模态怎样处理？

**60 秒主答**

原始附件先入租户对象存储，按内容验 MIME、恶意扫描，拦截路径遍历、归档炸弹、宏、脚本和不支持加密；在 无出站、资源限额沙箱中解析。优先确定性文本/OCR，再选最多 12 个安全页面，单次最多 4 图给 `VISION_EXTRACT`。输出只是 versioned EvidenceCandidate，不能成为指令。

**追问：限制是多少？**

每附件 20MB，文本/OCR 最多 50 页，视觉最多选择 12 页，每模型请求最多 4 图；加密、冲突或不可读内容进入人工复核。

## G. 评估、体验与运营

### 49. 如何评价 RAG，而不是只看回答准确率？

**60 秒主答**

分开评估索引、召回、排序、引用、生成和拒答。检索看 Recall@20、NDCG@10；证据看定位信息/ACL 和引用精确率；生成按主张计算证据-supported 速率；无答案/冲突看正确拒答率；线上再看草稿采用、编辑距离和处理时长。这样某个坏案例能定位到 top20、重排、装箱还是生成。

420个检索查询是按时间切分的隔离评测集合；调文本块/RRF/reranker只用独立校准-180，胜出者冻结后隔离评测只跑一次。FAQ模板和近重复通过MinHash+嵌入去除，索引冻结在查询当时可见版本。另有独立142个unique 应拒答案例 案例，138/142取seeds11/29/47的最差随机种子，不属于300/420。引用精确率/覆盖率来自预注册seed29的2,300个unique 声明；coverage2,249/2,300、严重 coverage186/186。

**追问：为什么不用一个 RAG 分数？**

一个总分会掩盖修复路径和高风险尾部。召回失败需要改索引，生成幻觉需要改约束，越权则是安全事故，不能相互平均。

### 50. 300-案例发布语料库怎么组成？

**60 秒主答**

100 个双语邮件分类、长线程和草稿；60 个 RAG 证据、冲突、无答案和引用；60 个邮件/附件/图像提示词注入；40 个图像、扫描 PDF、表格和视觉提取；40 个超时、OOM、模型切换、RAG 故障和队列恢复。独立评估器保存数据集/split 哈希、Model/能力配置/Prompt 清单、分母、rubric、评估器、随机种子、不透明案例 哈希和完成 receipts；原始内容案例 IDs/内容/labels只留在受限私有评测存储，不进入应用账本、GateIndex或Git。

**追问：300 够吗？**

它是发布回归集，不是覆盖世界。检索另有 420 个标注查询，线上经过授权、去标识的失败案例持续加入硬性集合；关键是分层、版本化和零容忍门，而非只追求样本总数。

### 51. 质量指标为什么这样选？

**60 秒主答**

- 风险子集案例级混淆 矩阵：TP=74、FN=1、FP=3、TN=122；最差随机种子召回率 98.7%、精确率 96.1%、specificity 97.6%，防止用“全判高风险”刷召回率。三个随机种子的决策级召回率为 223/225=99.1%，只用于稳定性分析，不当成独立样本。
- 分诊 Macro-F1 92.6%，避免普通类占比掩盖小类。
- 证据-supported 主张 2,270/2,300，98.7%，逐事实而非整封二元打分。
- 引用精确率 1,446/1,500，96.4%，保证引用真的支持陈述。
- 独立142个unique 证据不足-证据 案例的最差随机种子拒答率为138/142=97.2%；不把3 随机种子扩成426个独立样本。
- 视觉 关键字段 F1 92.3%，覆盖 40 个视觉案例中的金额、日期、联系人等字段。

安全项如越权写、关键无依据金额/日期/联系人和提示词注入提权是 0 容忍，不能用平均准确率抵消。“0”只指 60 个版本化安全案例 × 3 个固定随机种子中观察到 0 次，不等于对未知攻击的绝对安全保证。

### 52. 线上业务价值怎么证明？

**60 秒主答**

业务事件直接记录入站持久化、首次打开、草稿版本、确认、审批、发送动作和 SMTP 接受事实时间。六周试点中，处理时长中位数 12.4→5.6 分钟，首次发送响应 21→7 分钟；13,620/18,406=74%发送处理事件无需结构性重写，21,378/24,020=89% AI-草稿处理事件进入确认/审批，不要求发生编辑。指标按风险、降级状态和邮件类型分桶。

漏斗按处理事件去重为31,260→26,980→24,020→21,378→18,406，但业务主分析不用终态选择：42天人工 AI 关闭基线期=30,880，经过预先固定的非零且≤24小时过渡期后，42天试点期=31,260，随后还有三个独立7天跟踪期。每个 intake 的 `ActionabilityDecision` 在 exposure 前写入，只有闭集 NON_ACTIONABLE 被排除；UNKNOWN 保留并强制人工、AI 关闭。暂停/AI-不可用与所有 轮次 均纳入。只按 intake-rota 处理人、语言、前策略 category、relative week 等 pre-exposure 字段标准化；终态处理人/风险/草稿/复核/终态禁入。试点期终态/competing/censored 完整分解，非活动类业务字段 missing132/174 做 IPCW+MNAR 而不删；独立 `ActivityCoverageRecord` 若缺版本指向记录/证据链/角色覆盖，活跃时间/容量/总体拥有成本 直接 `NOT_ESTIMABLE`，不能用 IPCW 补救。响应-to-SMTP-accept 有独立20,140/20,380 试点组与已接受/competing/censored 计数。仅在 ActivityCoverage 硬门通过时，演练值才可报活跃时间未舍入差-3.554190659min/主模型-分析处理事件、总111,104min；¥51,264只支持六周边际容量-value/cost4.33x，另报¥1.10m program 总体拥有成本 与8.9月基础容量 payback，不称现金投资回报率。

**追问：采用率高就代表好吗？**

不。必须和主张 support、拒答、高风险召回率、撤销和编辑幅度一起看，否则流畅幻觉也会提高采用。

### 53. “74% 无结构性重写”怎么定义？

**60 秒主答**

基于版本化草稿与最终规范化 MIME：主题意图、主要事实、段落结构和行动要求保留，仅允许措辞、语气、局部顺序与格式调整。用确定性差异生成候选，再由抽样人工标注校准；不能只用字符相似度，因为同义改写和一个金额变化的风险完全不同。

**追问：为什么还看 89%？**

74% 衡量草稿接近最终稿，89% 衡量它是否进入确认/审批工作流。剩余未进入或未发送的部分可能是客户补充、合并工单、策略阻断或草稿质量问题，要分原因。

### 54. 如何设计用户可理解的降级体验？

**60 秒主答**

不展示技术栈错误，而展示状态、影响和下一步：`retrieval_degraded` 表示仍有证据但排序下降，建议检查引用；`evidence_unavailable` 表示没有证据，可人工处理或按策略阻断；`MODEL_SWITCHING` 表示草稿稍后恢复；`AI_UNAVAILABLE` 表示可继续人工链路；`DELIVERY_UNCERTAIN` 明确禁止重试并进入对账。

审批体验同样看尾部：P50/P95 为 2.7/14.2 分钟，3.8% 因新来信或字段变化过期，需要 re-复核；系统保留人工编辑并只 rebase 受影响字段，超过工作时段的 1.7% 自动转派/升级，而不是让用户重新写整封邮件。

**追问：为什么不隐藏降级保持顺滑？**

企业用户的信任来自可预测和可行动，不是永远返回一个流畅答案。

### 55. 共享邮箱体验最重要的三个点是什么？

**60 秒主答**

第一，责任明确：每个线程有一个处理人，租约/过期状态可见。第二，证据可检查：草稿旁能看到引用、冲突和缺口。第三，发送语义明确：普通确认、高风险独立审批、审批失效原因和 SMTP 接受/不确定状态都能解释。AI 的价值是减少查阅和撰写，不是增加一个需要照顾的聊天窗口。

**追问：用户绕开系统去腾讯邮箱客户端发送怎么办？**

试点不向个人发放客户端 password，服务凭据只挂载给服务商适配器；Sent reconciler 会将没有已知发送动作/Message-ID 的外发作为零容忍 unmanaged 安全事件并暂停/终止试点。但服务商超级管理员仍可能绕过，这是凭据与组织治理风险，不能假装由 Agent 完全消除，也不能把非零 bypass 当成采用率成功。

### 56. 什么是系统的 SLO，什么不是？

**60 秒主答**

生产SLO与发布容量证据分开。滚动-30-天 Mail 核心 良好/不良/排除=43,174/26/0，整数不良余17个；AI durably admitted=23,200、30秒内良好=23,038、排除=0，99.3017%→99.3%。5m+1h同时14.4x 分页，6h+3d同时2x 工单/freeze。同步 P9538秒、发送 commit240ms；不确定事件 4/4≤96分钟仍是有限样本。

**危险说法**

### 57. 如何观察一次坏草稿的完整链路？

**60 秒主答**

用关联 ID 串起线程/草稿版本、router 决策、能力配置/Model 清单、ContextManifest、MCP 会话、证据包哈希、模型-调用记录、风险/策略快照和人工最终版本。日志不记录原始敏感正文，只记录 scoped 对象 IDs、哈希、状态、耗时和经过授权的调试引用。这样既能定位阶段，又不把客户数据复制进普通日志。

**追问：模型切换后如何比较？**

每次重试是新的模型-调用记录，记录主/备证据产物和已降级状态；一个动作不会半途换模型。

### 58. 如果知识库更新后旧草稿用了过期证据怎么办？

**60 秒主答**

证据包固定文档版本、ACL/索引快照和哈希，并绑定到草稿审批。发送前策略和资源版本会重验；若业务规则要求最新版本且证据已撤销或过期，授权失效。审计仍能说明当时使用了哪个版本，但不会把旧内容冒充当前有效事实。

**追问：是否每次发送都重新 RAG？**

不盲目重跑生成。先检查绑定证据的有效性和策略；若失效，回到草稿/复核，而不是静默替换证据后沿用旧批准。

### 59. 这套系统最大的残余风险是什么？

**60 秒主答**

第一，单 A100 仍是 AI availability 单点，五分钟冷启动降级不是 HA。第二，SMTP 最终投递不可完全观测，只能诚实建模接受事实与 不确定事件。第三，单租户试点没有证明多租户运营和大规模向量检索成本。第四，人可能批准错误内容，所以系统提供证据、绑定和审计，但不能替代业务责任。

数据治理由试点期 TenantPolicy v1 与 LegalHold 决定。删除先生成 dry-运行 `DeletionPlan`，仅在 MailAdmin 确认、无保持、备份哈希验证后传播。唯一 RPO 证据是签名 `RecoveryPointManifest`：它原子绑定同一集群日志序列号/时间、应用/审计/评估高水位、叠加层、治理登记表、已消费账本、对象/评估检查点、密钥与候选项身份，且在包后、激活前补发布包后清单；零散 DB/对象版本指向记录或复制 延迟 不能替代。恢复门检查 `declared_failure_time-latest_verified_manifest.recovery_point_time≤15m` 及全部成员完整；三次试点期-大小演练最坏 RPO 8分42秒，从 declared 失败 `t0` 到人工链路43分钟。恢复后的非终态发送全部 `RECOVERY_SEND_HOLD`。

**追问：优先解决哪个？**

若扩大客户范围，先做双 GPU/节点推理与多租户资源隔离；如果仍是当前规模，则优先提高检索硬性 案例 和审批队列体验。

### 60. 如果再做一版，你会怎么演进？

**60 秒主答**

按触发条件演进，而不是堆功能：有第二家客户再做服务商能力 abstraction 与租户配额；GPU 降级影响 SLO 再做双节点推理；文本块/P95 过门再拆向量存储；累计 1,000 对合规草稿/终稿且提示词/RAG 改进饱和后再评估 LoRA。当前不会优先做通用自治工具、GraphRAG 或前端重构，因为它们不解决 V1 最核心的可控发送与证据问题。

## H. 压力面试：连续追问链

### 链 1：你说幂等，为什么还会重复发邮件？

1. 本地幂等只保证一个客户端命令对应一个回执。
2. 一次性授权只生成一个发送动作/发件箱事务记录/Job。
3. SMTP 是外部副作用，最终响应可能丢失。
4. 所以不声称恰好一次，而以 `DATA_STARTED` 划不可重试边界。
5. 模糊结果进入 `DELIVERY_UNCERTAIN`，旧 Action 永不重放。
6. 人工替换是新授权、新 Action、新 Message-ID，并关联旧事件审计。

**白板终点**：`authorization → SendAction → Outbox → Job → ProviderAttempt → acceptance/uncertainty → reconciliation`。

### 链 2：你说 MCP 安全，如果代理服务被攻破呢？

1. AuthorizationService 先签发 consume-once `AuthorizationContext`，绑定操作者/会话/租户/邮箱/资源/operation/router 模式/范围上限/代理服务 mTLS 身份/过期时间。
2. 代理服务不持有 signing 键、不能自报操作者/范围，只能在上限内请求更小子集；AuthorizationService-owned TokenIssuer 幂等返回同一回执/jti，它是密钥隔离适配器而非第二授权权威责任方。
3. 调用方不能传 租户/知识集合/ACL。
4. 令牌签发时只 sender-受约束到代理服务 mTLS；首次 MCP 使用时 PG 重放守卫原子绑定 `jti+claims_hash` 到新会话指纹。
5. RAG MCP 只有读取-仅 DB/对象凭据，management plane 是另一身份/网络/组合根。
6. PostgreSQL RLS 是防调用方过滤/bypass 的最后一层，但不能击败已被伪造的受信服务身份。

**承认边界**：代理服务运行时失守仍可滥用它已取得的合法 AuthorizationContext；mTLS/HSM 不能防已授权进程滥用。TokenIssuer 阻止它凭空伪造管理员操作者，但 AuthorizationService/signing 边界若失守，验签和重放守卫也无法识别“签名正确的伪造身份”。此时只能靠短期令牌、紧急 revoke/rotation、实时 ACL、审计和只读 blast radius 控制事故，不能声称绝对安全。

### 链 3：为什么不用一个更大的模型解决所有问题？

1. 权限和发送不是模型能力问题。
2. 单 A100 约束要求可预测的上下文/并发/视觉邮件信封。
3. 七个能力配置让资源、质量和降级能分别评估。
4. 35B 负责主质量，9B 只承担已验证子集。
5. 更大模型会减少余量、提高尾延迟和恢复时间。
6. 是否升级由业务案例、质量门和容量门禁共同决定，不由排行榜决定。

### 链 4：RAG 指标很好，为什么用户还大量编辑？

1. 检索正确只证明证据可用，不证明语气、策略和客户关系表达完全合适。
2. 区分事实编辑、结构编辑、语气编辑与客户新增信息。
3. 先看正确证据是否进入 top20/topK，再看装箱、主张 grounding 和能力配置。
4. 若只是风格编辑，不必牺牲可控性追求 100% 原样采用。
5. 业务目标是减少处理时间和风险，而不是消灭人的判断。

### 链 5：单卡故障五分钟，客服不是等不起吗？

1. `MODEL_SWITCHING` 期间新生成排队或提示人工，已有邮件同步/草稿编辑/审批/发送不受影响。
2. 五分钟是检查点冷切换上限，不是假装 GPU HA。
3. 同时常驻备模型会降低主路径余量，可能增加 OOM。
4. 若业务 SLO 不接受五分钟，正确演进是第二 GPU/节点，而不是在一张卡上做伪热备。

只画六个框：Client/企业微信、Mail 核心、PostgreSQL、RAG MCP、推理网关，以及作为外部边界的 腾讯 Provider。用粗线标出唯一写路径，用虚线标出只读证据。

### 2. 发送状态机

```text
DRAFTED
  -> REVIEW_CONFIRMED / APPROVAL_GRANTED
  -> SEND_AUTHORIZED (one-time, 5 min)
  -> SendAction + Outbox + Job
  -> SESSION_OPEN
  -> ENVELOPE_VALIDATED
  -> DATA_STARTED
  -> SENT | DELIVERY_UNCERTAIN
  -> reconciliation observation
```

强调 `DATA_STARTED` 之后没有自动重试箭头。

### 3. RAG 安全链

```text
WeCom actor/resource
  -> Tool Broker computes scope
  -> mTLS + short-lived token
  -> replay guard
  -> MCP scope + current ACL
  -> read-only DB/RLS/object credential
  -> EvidenceBundle
```

### 4. A100 降级状态机

```text
PRIMARY_READY
  -> PRIMARY_RESTARTING (once, 32K/c1)
  -> FALLBACK_LOADING (primary VRAM = 0)
  -> DEGRADED (4/7 Profiles)
  -> operator canary + 10 min
  -> PRIMARY_READY

failure -> AI_UNAVAILABLE
```
