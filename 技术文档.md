# 安全外发与邮件协作 Agent 技术文档

## 1. 当前定位

当前项目定位为企业安全邮件协作与知识问答 Agent。它不是单点 DLP 工具，也不是泛化邮箱客户端，而是坐在员工和外部沟通渠道之间，统一处理：

- 企业知识问答
- 邮件草稿与安全外发
- DLP 检测、审批、真实 SMTP 发送
- 企业邮箱 IMAP 只读同步、摘要和回信草稿
- 上传内容分析
- Hermes-style memory
- 多用户 / 租户上下文、权限、限流、队列和可观测性

旧版 LeetCode V1 Agent、旧 sensitive workflow 和 `/problems /ingest /plan /execute /chat` 接口已经移除。Apple 歧义消解、长文档预算和框架观点等 Labs/MCP 工具作为受控扩展保留，不进入企业事实问答主链。

所有开发、回归和验收默认在 Docker 容器内完成。

## 2. 服务拓扑

```text
Streamlit user workspace 8511 / governance console 8512
-> FastAPI api 8010
-> Redis / Celery queues
-> worker
-> PostgreSQL / SQLite local files
-> Chroma 8011
-> Prometheus 9091
```

核心容器：

- `web`: Streamlit 多人试用前端
- `api`: FastAPI 主服务
- `worker`: Celery worker，处理 DLP、发送、收件、EnterpriseRAG ingest / benchmark
- `redis`: queue、rate limit、event stream
- `postgres`: 任务、会话、收件、memory 等结构化存储
- `chroma`: dense vector store
- `prometheus`: 指标采集

## 3. 多用户与权限模型

统一身份对象是 `ActorContext`：

```text
tenant_id
user_id
workspace_id
roles
session_id
conversation_id
```

身份来源：

- Web 端绑定腾讯企业邮箱。
- API 请求可通过 `X-Tenant-Id / X-User-Id / X-Workspace-Id / X-Roles` 注入。
- 无身份时 fallback 到 `local-dev / local-user / default`，保证本地 Docker demo 可用。

权限边界：

- EnterpriseRAG 检索带 `tenant_id / workspace_id` filter。
- conversation / task / memory 按 user / workspace / tenant 分层隔离。
- mail send、DLP approval、RAG ingest / benchmark、policy update 等 side-effectful 动作必须检查 role。
- 权限失败输出结构化 observation，由 renderer 生成用户可见说明。

## 4. `/agent/chat` 主链路

当前 `/agent/chat` 采用 Fast Path + ReAct Slow Path 的混合架构：

```text
request
-> build ActorContext
-> permission check / rate limit
-> L0 router
-> Fast Path or Slow Path
-> tool call / memory read
-> TypedObservation
-> final renderer
-> Agent Verifier
-> Agent Trace Evaluator
-> memory write / metrics / response
```

Fast Path 处理低成本高确定性请求：

- persona / capability
- contextual memory
- upload analysis
- enterprise fact
- mail / task status

Slow Path 使用 ReAct controller：

- `think`
- `read_memory`
- `call_tool`
- `request_confirmation`
- `direct_answer`
- `ask_clarification`

工具能力通过 dynamic registry 暴露；工具元信息包括：

- `read_only`
- `side_effectful`
- `requires_confirmation`
- `returns_observation_type`
- `reads_from`
- `writes_to`

side-effectful 工具不得直接执行，必须进入 confirmation 节点。

历史清理边界：

- `app/graph.py` 只保留共享 `get_llm()` client 工厂。
- 已删除旧 `unified_agent.py / hybrid_router.py / unified_tools.py` LangGraph V1 栈。
- 已删除旧 `sensitive_workflow.py / workflow_store.py` SQLite workflow 栈；现役治理统一使用 PostgreSQL `/tasks`、Celery worker、typed observation 和治理台。
- 已删除旧 LeetCode corpus API；启动时统一语料 seed 只保留 Labs/DLP 所需证据，不再写入 LeetCode problem 文档。

## 5. Typed Observation Contract

所有工具、memory read、retrieval、mail state、failure recovery 都尽量统一为 typed observation：

```text
observation_type
status
source
grounding_kind
summary
payload
provenance
confidence
missing_fields
constraints
side_effects
citations
actor_context
```

设计目的：

- renderer 不再读取业务模板。
- debug 能看到同一套结构。
- verifier / trace evaluator 可以做统一审计。
- 权限失败、依赖失败、confirmation、memory 边界都能被同一种观察值表达。

## 6. Final Renderer 与 Guardrail

用户可见回答遵循 observation-first：

- 规则层负责状态、约束、权限、来源边界、工具调用。
- final renderer 基于 observations 和 working memory 生成自然语言。
- fallback 只用于 LLM 不可用、硬超时或安全失败，不作为主路径文案系统。

Agent Verifier 在最终回答前后做结构化检查：

- 权限失败是否被说成成功
- 企业事实是否缺少 citations
- memory 是否被当成企业事实来源
- confirmation 是否被绕过
- attachment-only 内容是否泄漏到可见回答

如果 verifier 判定需要修正，系统会追加 `agent_verifier_verdict` observation，并让 renderer 重写一次。

## 7. Agent Trace Evaluation

Trace evaluator 评估 Agent 行为本身，而不只是答案文本。它读取：

- `tool_calls`
- `tool_observations`
- `memory_reads`
- `citations`
- `pending_confirmation`
- `actor_context`
- `route / planner / termination debug`

当前检查项：

- 工具选择是否符合 `required_grounding` 和 router intent
- side-effectful 工具是否缺少 confirmation
- memory 是否替代了 EnterpriseRAG citation
- observation 是否跨 tenant / workspace
- 是否重复调用 EnterpriseRAG / memory_search 等重工具
- tool failure / partial failure 后是否有 recovery / fallback observation

输出字段：

- `agent_trace_evaluation.ok`
- `score`
- `issues`
- `tool_counts`
- `failure_count`
- `recovery_observation_present`

该结果会写入 `task_plan.agent_trace_evaluation`，也会作为 `agent_trace_evaluation` observation 进入 debug。

## 8. Failure Recovery 与 Circuit Breaker

统一失败观察值是 `dependency_failure`：

```text
service
operation
error
fallback_strategy
retry_count
circuit_state
severity
```

首批接入：

- `LLM final_renderer`: retry 后失败则 deterministic fallback，并记录 `agent_llm_errors_total / agent_renderer_fallback_total`
- `reranker`: CrossEncoder 失败降级 heuristic rerank
- `SMTP`: retry 后失败进入 `delivery_deferred / send_failed`
- `Celery enqueue`: retry 后失败抛出结构化 enqueue failure
- `Redis`: rate limit / queue health 失败时 fallback-open 或返回 degraded queue health
- `Chroma`: dense recall 失败时允许 sparse 继续
- `SQLite FTS`: sparse recall 失败时允许 dense 继续

Prometheus 指标：

```text
agent_dependency_failures_total{service,operation,fallback_strategy}
```

这个指标用于监控聚合，`dependency_failure` observation 用于单次请求审计。

## 9. EnterpriseRAG 架构

EnterpriseRAG 是企业事实问答主路径。旧 LeetCode/problem_id 语料不再作为企业知识基础。

目录：

- `app/enterprise_rag/core`: query planner、retrieval orchestrator、evidence pack、answer composer
- `app/enterprise_rag/ingestion`: loader、normalizer、chunker、indexer、manifest
- `app/enterprise_rag/libs`: sparse index、reranker、metadata、scoring、text cleaning
- `app/enterprise_rag/eval`: benchmark、casebook

检索链路：

```text
query
-> build_retrieval_plan
-> dense recall: Chroma + bge-m3
-> sparse recall: SQLite FTS5 + BM25
-> merge candidates
-> rerank: bge-reranker-v2-m3
-> evidence selection
-> sentence-level supporting facts
-> canonical_facts / core_facts / answer_slots
-> LLM structured answer
```

Adaptive budget：

- `small`: 明确事实 / 字段查询
- `medium`: 普通语义问答
- `large`: recommendation / constrained / conflicting
- `expanded`: 第一轮证据不足时触发二阶段扩展

调试字段：

- `retrieval_stage_debug`
- `rerank_debug`
- `supporting_fact_details`
- `canonical_facts`
- `question_focus`
- `core_facts`
- `answer_slots`
- `answer_debug`

## 10. EnterpriseRAG Ingestion 与缓存失效

文档级缓存失效已接入：

1. 本批 ingest 先收集 `doc_id`。
2. Chroma enterprise collection 按 `doc_id` 删除旧 chunks。
3. SQLite FTS5 按 `doc_id` 删除旧 rows。
4. 重新 chunk / embed / upsert。
5. manifest 记录 replaced doc ids、chunk counts、content hash、replace_existing。

这样避免同一文档旧版和新版 chunk 同时存在，减少 RAG 数据打架。

## 13. Hermes-style Memory

Memory 分四层：

- `session_transcript`: 近期原始会话
- `turn_summary`: 每轮结构化摘要
- `workspace_memory`: README、todolist、技术文档、项目规则、prompt、policy
- `user_model`: 用户偏好和长期记忆候选

Conversation memory 与历史 LeetCode 语料已经拆分。旧实现把 runtime memory 写入 `CHROMA_COLLECTION=leetcode_rag_v1`；当通用 embedding 切换到 `bge-m3` 后，旧 collection 的 512 维向量与当前 1024 维向量发生冲突。通用语料已切到 `CHROMA_COLLECTION=leetcode_rag_bge_m3_v1`，conversation memory 则使用独立版本化 collection：

```text
CONVERSATION_MEMORY_CHROMA_COLLECTION=conversation_memory_bge_m3_v1
CONVERSATION_MEMORY_COLLECTION_VERSION=bge-m3-1024-v1
CONVERSATION_MEMORY_EMBEDDING_DIMENSION=1024
```

迁移策略采用 copy + re-embed + switch：

1. 从旧 collection 只读提取 `is_runtime_memory=true` 文档。
2. 使用当前 `bge-m3` 重新向量化。
3. Upsert 到独立 conversation memory collection。
4. 保留旧 collection，不原地删除，便于回滚。
5. 新写入的 turn summary、merged summary 和历史兼容 summary 全部进入新 collection。
6. 重复执行时比较 content hash、模型、维度与 schema version，未变化记录跳过 embedding。

Docker 内迁移与验证：

```powershell
docker compose exec -T api python scripts/migrate_conversation_memory_collection.py --source leetcode_rag_v1
docker compose exec -T api python scripts/conversation_memory_migration_regression.py
```

结构化 turn memory 包含：

- `summary`
- `intent`
- `entities`
- `files_uploaded`
- `risk_level`
- `memory_scope`
- `provenance`

Memory 使用边界：

- context / preference / project convention 可以来自 memory。
- enterprise facts 必须来自 EnterpriseRAG citations。
- 高风险偏好和策略类记忆默认 pending，不自动改变工具、审批或发送行为。

## 14. Workspace Retrieval Policy

Workspace memory 不再所有文件都走 hybrid search。

策略：

- README / todolist / 总体要求 / 明确 `.md` 文件：exact path + FTS
- prompt / config / policy / memory note：metadata + FTS
- 架构、设计、为什么、如何：semantic / hybrid
- 不确定时 bounded hybrid，不无限放大 top_k

同步策略：

- hash / mtime 增量检测
- 未变更文件跳过 chunk 和 vector upsert
- 删除或重命名触发旧 chunk 清理

## Mail Provider Abstraction (M3)

M3 adds a formal provider boundary for Mail Agent V2.

Core contract:

- `MailProviderCapabilities`: declares search/read/thread/label/sync/send support.
- `MailProviderResponse`: normalized provider result with status, retryability, uncertainty, and optional recovery observation.
- `MailProviderResponse.to_observation(...)`: converts provider result into typed observation for renderer / trace / governance flow.
- `MailProvider`: protocol covering `search_messages`, `read_message`, `list_threads`, `read_thread`, `sync_mailbox`, `send_message`, `apply_label`, and `get_health`.

Adapters:

- `FakeMailProvider`: deterministic test provider with injected failure modes.
- `CurrentImapSmtpMailProvider`: adapter over current local inbound store and SMTP send path.

Safety boundary:

- Contract regression disables current-provider external sync/send by default.
- Write gaps such as labels return explicit `unsupported` plus `provider_write_supported=false`.
- External send remains controlled by existing confirmation / DLP / task worker workflow.

Regression:

```powershell
docker compose exec -T api python scripts/mail_provider_contract_regression.py
```

## Mail Normalization (M4)

M4 standardizes inbound mail objects before they are consumed by Mail Agent tools, provider adapters, UI models, and governance/debug surfaces.

Persistence changes:

- `inbound_mail_messages.thread_id`
- `inbound_mail_messages.provider_thread_id`
- `inbound_mail_messages.body_text`
- `inbound_mail_messages.body_html_sanitized`
- `inbound_mail_messages.body_preview`
- `inbound_mail_messages.labels_json`
- `inbound_mail_messages.attachments_json`
- `inbound_mail_messages.headers_json`

Normalization rules:

- HTML mail is never treated as trusted raw UI content.
- Visible text is extracted for DLP, summary, preview, and renderer use.
- Sanitized HTML removes script/style/iframe-like blocks, event handler attributes, and `javascript:` links.
- Attachments are metadata-only at this layer; attachment body content remains outside `body_text`.
- Local thread fallback uses provider thread hints first, then subject plus participants.
- Label writes that the current IMAP/SMTP provider cannot perform are explicit `unsupported` observations with `provider_write_supported=false`.

Regression:

```powershell
docker compose exec -T api python scripts/mail_m4_normalization_regression.py
```

## Mail Reliability and DLQ (M5)

M5 adds a durable dead-letter and replay-safety layer for Mail Agent side effects.

Storage:

- `mail_dead_letter_queue.dlq_id`
- `mail_dead_letter_queue.task_id`
- `mail_dead_letter_queue.operation`
- `mail_dead_letter_queue.payload_digest`
- `mail_dead_letter_queue.last_error`
- `mail_dead_letter_queue.attempt_count`
- `mail_dead_letter_queue.safe_replay_allowed`
- `mail_dead_letter_queue.recovery_hint`
- `mail_dead_letter_queue.actor_context`
- `mail_dead_letter_queue.payload_snapshot`
- `mail_dead_letter_queue.replay_count`
- `mail_dead_letter_queue.replay_status`
- `mail_dead_letter_queue.replay_result`

Replay rules:

- Replay is allowed only when `safe_replay_allowed=true`.
- Replay preserves the original task and idempotency key.
- Replay moves the task to `queued_for_send`; enqueueing the worker remains a separate governed action.
- SMTP uncertain delivery is not replay-safe by default because the provider may already have accepted the email.

Metrics:

- `agent_mail_dlq_created_total`
- `agent_mail_dlq_replay_total`

Regression:


## Mail UI and Governance Separation (M6)

M6 separates user-facing mail work from governance and operations.

Surfaces:

- `8511` is the user workspace. It keeps chat, inbox status, draft review, explicit user confirmation, simplified task progress, and renderer-generated recovery guidance.
- `8512` is the governance console. It owns high-risk exception approval/rejection, task timeline, provider health, queue health, recovery observations, DLQ safe replay, and harness diagnostics.
- Raw tool calls, trace JSON, token/cost diagnostics, DLQ replay, and queue/provider debugging do not appear in the normal `8511` user panel.

Backend endpoints:

- `GET /admin/task-stats`
- `GET /admin/mail-provider-health`
- `GET /admin/queue-health`
- `GET /admin/mail-dlq`
- `POST /admin/mail-dlq/{dlq_id}/replay`
- `GET /admin/mail-harness-summary`

Recovery contract:

- Unsafe DLQ entries return a blocked replay observation.
- Safe DLQ entries can be moved back to `queued_for_send` and then enqueued to the email worker.
- If enqueueing fails, the endpoint returns a dependency failure observation and keeps the DLQ entry auditable.

Regression:

```powershell
docker compose exec -T api python scripts/mail_m6_ui_governance_regression.py
```
